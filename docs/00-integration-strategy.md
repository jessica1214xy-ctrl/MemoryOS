# 扩展设备记忆代理 · 终端形态集成与跨端协调方案

> 文档定位：本方案回答"设备记忆代理应优先集成到哪种终端形态"，并设计多端统一的身份 / 数据 / 体验协调机制。是 PRD、设计、端到端文档的上位决策依据。

---

## 1. 背景与目标

MemoryOS 当前为 Web MVP（跨设备时间线 + 个人知识库问答 + 主动提醒），数据由模拟事件流驱动。要成为"真正的第二大脑"，必须**接入用户真实使用的终端**，持续自动捕获跨设备上下文，并在任意设备上无缝续接。

本方案目标：
- 选定**主集成终端形态**，在"功能承载 / 用户触达 / 开发成本"三角中取得最优解；
- 设计**多端统一协调机制**，保证身份、数据、体验在原生 App、微信小程序、其他小程序之间一致；
- 为后续 PRD、设计、端到端文档提供统一约束。

---

## 2. 终端形态对比

| 维度 | 原生 App（iOS / Android） | 微信小程序 | 其他小程序（支付宝 / 抖音 / 百度） |
|------|--------------------------|------------|-----------------------------------|
| **功能承载（系统能力）** | 强：可监听通知、读取剪贴板、后台同步、文件/网页系统级收藏、本地向量索引 | 中：仅能在微信内捕获聊天/收藏/文件，无后台与系统级能力 | 弱～中：依赖各自宿主，能力各异，普遍弱于微信 |
| **功能承载（跨 App 捕获）** | 强：可跨任意 App 捕获上下文 | 弱：仅在微信生态内，无法触达系统其他 App | 弱：仅宿主生态内 |
| **用户触达** | 弱：需主动下载安装，获客成本高 | 强：微信内即开即用，可分享/转发/会话卡片触达 | 中：宿主内流量，场景依赖性强 |
| **开发成本** | 高：双端原生或跨端（RN/Flutter），审核慢、迭代周期长、维护双栈 | 低：一套小程序框架，微信审核快，热更新灵活 | 中：各平台规范不同，需多端适配 |
| **数据回流价值** | 高：最完整的个人上下文 | 高（对微信场景）：直接拿到导师聊天、收藏等核心碎片 | 中：补充性来源 |
| **典型适用场景** | 重度用户、系统级自动捕获、离线优先 | 大多数用户的首触入口、微信上下文捕获 | 特定生态内的轻量触达 |

### 关键结论
- **微信是目标用户（研究生/知识工作者）最高频的"上下文发生地"**：与导师的微信沟通、微信收藏的论文，恰是本产品最关键的记忆来源。原生 App 拿不到微信内聊天，小程序天然能拿到。
- **原生 App 能补小程序之短**：后台同步、剪贴板/通知/跨 App 文件捕获，是"无感自动记忆"的体验上限。
- **其他小程序 ROI 偏低**：作为 Phase 2 触达补充，不宜早期投入。

---

## 3. 推荐主集成形态

**主推：微信小程序（Primary）；原生 App 为深度集成补充（Secondary）；其他小程序 Phase 2 扩展。**

理由：
1. **触达即价值**：零安装门槛，用户在微信里就能把"和导师聊到哪、收藏了什么"自动沉淀，首触转化最高。
2. **场景契合**：微信上下文是本产品 P0 价值来源，小程序是唯一能在合规范围内捕获它的形态。
3. **成本可控**：一套小程序框架快速验证留存与核心价值，避免一上来双端原生的高投入风险。
4. **原生 App 补位**：面向"想要无感自动记忆"的重度用户，提供系统级捕获与后台同步，作为付费/Pro 层。

> 形态优先级：**微信小程序 → 原生 App → 支付宝/抖音小程序**。

---

## 4. 多端统一协调机制

统一原则：**一套账户、一份数据、一致体验**。任一终端都是"同一用户记忆"的一个视图与采集器。

### 4.1 身份一致性
- 统一账户体系：`user_id` 为唯一主键；微信 OpenID、原生 App 设备 ID、手机号均映射至同一 `user_id`。
- 登录：微信小程序走微信 OAuth；原生 App 走手机号/微信联合登录；首次绑定自动合并。
- 设备注册：每台终端首次激活生成 `device_id`，登记设备类型（lab_computer/phone/tablet/wechat/email/native_app）与能力清单，供采集策略与续接判断使用。
- 隐私：多端共享记忆前需显式授权；支持"按设备/按应用"粒度开关与一键撤销。

### 4.2 数据一致性
- 中心化同步服务（沿用 CloudBase 架构）：所有终端事件统一写入同一时间线，服务端按 `user_id` 隔离后再检索。
- 采集层标准化：各终端捕获的异构数据（微信聊天片段 / 小程序收藏 / 原生剪贴板）统一映射为 `TimelineEvent`（已定义类型），保证下游一致。
- 冲突与合并：以"语义合并"优先（同一论文的不同设备片段聚合成一条记忆），时间戳冲突采用服务端权威 + 客户端本地队列补偿。
- 离线优先：终端本地队列缓存，恢复网络后增量上报；知识库向量索引在服务端统一构建。
- 多端续接（F4 核心）：断点事件带 `device_source`，用户在新设备打开时，服务端返回"上次在 X 设备做到哪"并提供一键续接入口。

### 4.3 体验一致性
- 设计 Token 统一：所有终端复用同一套 Design Token 与组件库（Lucide 图标、禁紫粉渐变、零硬编码色）。
- 导航与信息架构对齐：时间线 / 知识库 / 提醒 / 问答四模块在各端保持同一心智模型，按终端特性做响应式裁剪（小程序底部 TabBar、原生 App 底部导航 + 小组件）。
- 提醒统一分发：提醒卡片在"当前活跃设备"优先推送，已处理状态跨端即时同步（原生 App 系统通知 + 小程序订阅消息 + Web 站内卡片三通道去重）。
- 能力梯度呈现：小程序展示核心捕获与问答；原生 App 额外展示系统级自动捕获开关与离线记忆。

## 5. 实施路径（里程碑）

| 阶段 | 形态 | 关键交付 |
|------|------|----------|
| M1 | 微信小程序 | 微信上下文捕获（聊天/收藏/文件）+ 四模块只读/轻交互 + 统一登录 |
| M2 | 统一后端 | 多端账户合并、设备注册、中心化同步、续接 API |
| M3 | 原生 App | 系统级捕获（剪贴板/通知/跨 App 文件）、后台同步、Pro 能力 |
| M4 | 跨端协调打磨 | 提醒去重分发、离线队列、体验一致性验收 |
| M5 | Phase 2 | 支付宝/抖音小程序触达扩展 |

---

## 6. 风险与开放问题

- 微信数据合规边界：聊天内容捕获需明确授权范围与最小化原则，避免过度索取。
- 小程序后台能力缺失：微信内无法后台同步，需以"打开即同步 + 订阅消息提醒"弥补。
- 原生 App 双端成本：建议先用跨端框架（如 React Native / Flutter）控制投入。
- 多端续接的"误续接"：需用户确认而非自动跳转，避免打断。
